## 必须修正

**N02-01，P1：D4并未保证截断前的全局档位顺序。**

常量4/3/2不能压住没有该上界的BM25正文分数；“高于一般正文”不是充分条件。反例：limit=1，2个正文-only文档分数都高于4，另有一个整名命中文档得4；即使取limit+1，候选也只有两个正文文档，之后stable-sort找不回整名文档。高档之间也需覆盖多词组相加与档位定义差异。

删除“越档后只在呈现层重排并记录即可交付”的退让，它与proposal/spec的Top-N保证冲突。0.3必须选可证明策略，例如互斥档位分次查询、共享同一reader/过滤器后按档补足；或单查询的有界评分/全局排序方案并给出严格论证。不能仅换一组更大的boost。全流程成本纳入B0门槛。同分path tie-break如果是全局承诺，也不能只在已截断窗口里排序。

需写清单词/多词的整名、前缀及子串定义（是否包含扩展名、原输入空白、词序）；“逐词最高档”与“完整查询匹配整名”不能混用。验收加入limit=1/2且有超过取样窗口的高正文/低档样本。

**N02-02，P2：D4/tasks3.2把name_raw误认为存储字段。**

当前LuceneIndexer对文件/目录均以 `Field.Store.NO` 写name_raw（约276/303行）；SearchResult也不返回该字段。不能直接从Document/结果模型读取其值做重排。可从已存储name/结果name按同一Locale.ROOT规范计算展示档位，或明确别的可实现方案，但这不解决N02-01的全局Top-N问题。0.3不能偷偷把name_raw改为stored或新增DocValues来实现“零索引变更”路线。

**N02-03，P2：hasMore默认false与unknown未形成唯一类型/传输契约。**

false应表示已知无更多；包装旧search所得的size不足以证明它。明确三态（如Boolean null或枚举）与默认实现：UNKNOWN不能伪装FALSE；HTTP未知时省略可选标记或明确null，UI不声称结果完整；已知TRUE/FALSE由limit+1判定。hasMore与truncated若同时输出必须一致。补默认兼容实现未知、limit恰好相等、limit+1、最大HTTP limit及过滤/删除位用例。

**N02-04，P2：D6“程序化setText立即doSearch”会与历史回写/初始化冲突。**

当前MainWindow.addToHistory在完成结果后调用setQueryText(q)（约2231行），初始化/内部同步也会改编辑器。若这些程序化写入都触发立即查询，可能循环查询或重复请求，亦与acceptance“程序化setText不产生额外提交”矛盾。明确三类事件：用户键入→失效+防抖；用户明确提交/历史选择/范围过滤动作→取消timer后一次提交；初始化/历史模型刷新/内部文本恢复→只更新控件、不提交。历史刷新保留新草稿及光标。任务与用例同步，不把每次setText当一次用户意图。

**N02-05，P2：Modified Capabilities仍写无，与DS-03评分兼容承诺冲突。**

已接受主规格DS-03要求保持合法关键词/评分语义；B有意改变默认FUZZY名称匹配及排序。0.3应列directory-scoped-search为受影响能力，提供DS-03完整MODIFIED delta，明确B名称体验授权下的兼容例外，保留目录/类型过滤、响应兼容及其他场景。不要改现有主规格去迎合未实施B；同步发生在B未来验收归档时。

**N02-06，P3建议：输入分类补齐可直接执行边界。**

明确64按Unicode码点计数而非UTF-16 char；AND/OR/NOT按独立词法token识别，避免把包含AND字符的普通名称误判；明确Unicode空白分词。用户英文UI应继续使用英文截断提示，中文文案仅作为语义说明。以上可由0.3技术设计一次固定，不新增功能。
